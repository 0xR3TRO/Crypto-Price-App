Audyt techniczny repozytorium

Raport oparty wyłącznie o strukturę plików i dokumentację repo.

Ceny Audyt techniczny

# 1. Executive Summary

  • Typ projektu: statyczna aplikacja web (HTML/CSS/JS) pobierająca ceny z CoinGecko API.
  • Największe problemy:
    • Brak testów automatycznych i pipeline CI/CD.
    • Cała logika w jednym pliku JS — brak warstw i modułów.
    • Brak obsługi błędów, stanu ładowania i limitów API.
    • Dokumentacja opisuje inny stack (React/Node) niż kod.
    • Brak informacji o bezpieczeństwie i deploymencie.
  • Największe dźwignie poprawy (top 5):
    1. Wprowadzenie struktury src/ i modułów oraz minimalnego builda.
    2. Dodanie testów (unit + e2e) i bramek jakościowych w CI.
    3. Obsługa stanów UI (loading/error/empty) + retry/caching.
    4. Ujednolicenie dokumentacji z realnym kodem i roadmapą.
    5. Podstawowe security: skan zależności, CSP, polityka sekretów.

# 2. Odczyt repo z samej struktury i dokumentacji

Co wiadomo na pewno

  • Repo zawiera statyczne pliki: index.html, Directories/script.js, Directories/style.css.
  • W katalogu Media & Images są ikony kryptowalut używane w UI.
  • Skrypt JS pobiera ceny 6 kryptowalut z CoinGecko API.
  • Dokumentacja (PL/EN) opisuje wymagania funkcjonalne i architekturę w ujęciu ogólnym.
  • Brak widocznych narzędzi build/test/lint (np. brak package.json).

Założenia (jawnie)

  • Założenie: aplikacja jest hostowana jako statyczna strona (np. GitHub Pages, S3).
  • Założenie: brak backendu i bazy danych w tym repo.
  • Założenie: brak logowania i profili użytkowników (nie wynika z kodu).

Luki informacyjne

  • Brak informacji o środowiskach, release’ach i rollbacku.
  • Brak polityki bezpieczeństwa, zarządzania sekretami i SLA.
  • Brak licencji, właścicieli komponentów i procesu zmian.
  • Brak metryk jakości i observability.

# 5. Docelowa architektura i struktura repo

Proponowane bounded contexts / moduły

  • Market Data — pobieranie i normalizacja danych z API.
  • Watchlist — ulubione aktywa (local storage).
  • Alerts — progi cenowe i powiadomienia.
  • UI Core — komponenty, layout, style.

Kontrakty między modułami

  • MarketDataClient zwraca ustandaryzowany model Quote.
  • WatchlistStore operuje na AssetId i emituje zmiany.
  • AlertsService subskrybuje Quote i publikuje eventy.

Docelowe drzewo katalogów (przykładowe)

/
├─ src/
│  ├─ app/
│  ├─ assets/
│  ├─ components/
│  ├─ features/
│  │  ├─ market-data/
│  │  ├─ watchlist/
│  │  └─ alerts/
│  ├─ services/
│  ├─ styles/
│  └─ tests/
├─ docs/
├─ infra/
└─ public/

Zasady „co gdzie trafia”

  • Logika domenowa w features/*, UI w components.
  • Integracje z API w services.
  • Statyczne zasoby w assets i public.

# 6. Proces wytwarzania end-to-end

  • Git workflow: GitHub Flow (krótkie feature-branch, PR z review).
  • Definition of Ready: jasno opisany problem, akceptacja zakresu, kryteria sukcesu.
  • Definition of Done: testy przechodzą, brak krytycznych luk bezpieczeństwa, aktualne docs.
  • Quality gates: lint + testy + skany bezpieczeństwa + Lighthouse CI.
  • Wersjonowanie: SemVer + tagi releasowe.
  • Release strategy: automatyczny deploy po merge do main.
  • Rollback / hotfix: szybki rollback na poprzedni tag + hotfix branch.

# 9. Backlog techniczny (priorytetyzowany)

  • P0: dodać CI z lint + test (S/M) — redukcja ryzyka regresji i szybsze PR.
  • P0: ujednolicić dokumentację z realnym stackiem (S) — lepszy onboarding.
  • P1: wydzielić warstwę services dla API (M) — łatwiejsze testy.
  • P1: dodać cache i obsługę błędów (M) — stabilność UI.
  • P2: observability (Sentry, Web Vitals) (M) — szybka diagnoza.

# 10. Metryki sukcesu

  • DORA: wdrożenia/tydzień, lead time, MTTR, change failure rate.
  • Jakość kodu: coverage ≥ 70% (Założenie: obecnie 0%).
  • Niezawodność: % błędów API < 1%, uptime ≥ 99.5%.
  • UX: LCP < 2.5s, CLS < 0.1.
  • Postęp co sprint: raport z CI + Lighthouse + liczba błędów z Sentry.
